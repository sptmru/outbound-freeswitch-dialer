## A01.1 — Current lock inventory

Notation: `T` = one explicit SQL transaction, locks released on COMMIT/ROLLBACK; `S` = session lock on the owning PostgreSQL connection, released explicitly or when that connection dies; `Q` = one autocommit statement, whose implicit row/FK/index locks end with the statement. A pool client is not itself a transaction. Ordinary SELECTs below are snapshots, not exclusion locks. INSERT/UPDATE/DELETE also take implicit row, unique-index and foreign-key locks; these must be considered when migrating, even without `FOR UPDATE` text.

### Current graph and review findings

Arrows mean a lock can still be held when the next lock is acquired; dotted conceptual transitions below are separate transactions. This graph includes implicit row writes where they affect the lifecycle. It is not a claim that the current application already implements the target order.

```text
start T:       maintenance → media → agent → existing call / contact → inserts
finalize T:    agent → call → legs/events → contact → agent(already held)
VM claim T:    audio → call → recording KEY SHARE → event
audio edit T:  audio → campaign → recording
audio delete:  audio → recording → reference snapshots
user admin T:  media → user → agent → supervisor endpoint
supervisor T:  media → supervisor-session INSERT (FKs to user/call)
supervisor S:  media → [ESL + Q session updates] → explicit unlock
event T:      call → event/leg; no agent lock afterward
retention:    retention S → [file work + separate T call/PCAP/delete]
operations:   host flock → maintenance flag write; flag COMMIT → active-call check
```

The shared `agent → call` order must survive until every participant is migrated. Adding admission after either row creates an inversion with migrated starts. Supervisor's session media lock cannot become an outer wrapper around admission. The immediate voicemail release uses multiple autocommit statements and cannot be treated as the event release transaction. Campaign and suppression state can change independently of current route snapshots. The current pool has `max:10`, `connectionTimeoutMillis:5000` in [db.ts](../apps/api/src/db.ts); retention and postcommit actions already lease clients, so session execution locks need a bounded connection budget (A06/C03).

For multiple keys in one group, deduplicate and acquire in deterministic order; do not rely on bulk UPDATE planner row order. A changed discovery set requires ROLLBACK, release execution locks, rediscover, and retry from rank 0 with a bounded policy. Even if a newly discovered owner happens to sort later, do not add it after locking the call. Event persistence may append historical evidence outside the arbiter, but eligibility, slot release, owner changes and capacity transitions must use it.

The target graph is `execution → maintenance → admission → audio/config → media/user → agents → slots → calls → children → capacity → contacts`. Paths can omit groups; none add a backward edge. Between transactions an executor may retain only rank 0. Thus no target wait-for cycle can arise from the listed application locks if every participant follows this contract. FK/unique and DDL waits still require database validation; this is a source-level partial-order argument, not an executed deadlock test.
